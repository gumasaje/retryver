# Retryver 초기 요구사항 초안

HTTP 이벤트 전달에서 관찰한 결과 불확실성과 재전송 문제를 바탕으로 Retryver의 초기 요구사항과 책임 경계를 정리한다.

접수·전달 방식은 초기 요구사항으로부터 도출한 잠정안이며, 구현과 검증을 통해 구체화한다.

## 배경과 실험에서 확인한 사실

HTTP 요청에서 Sender가 관찰한 결과와 Receiver의 실제 처리 결과는 일치하지 않을 수 있다. 사전 HTTP 직접 전달 실험에서는 응답을 확인하지 못한 요청이 실제로 처리됐고, 같은 논리적 이벤트를 재전송했을 때 다시 처리되는 상황을 관찰했다.

실험은 같은 컴퓨터의 loopback 통신과 메모리 카운터로 수행했다. Sender의 timeout은 2초, Receiver의 지연은 5초였으며, 재전송은 Receiver를 재시작하지 않고 같은 Event ID로 수동 실행했다.

| 실험 | Sender가 관찰한 결과 | Receiver에서 확인한 결과 |
| --- | --- | --- |
| 2026-09-28 `delay-before` | 약 2초 후 timeout | 약 5초 후 처리 건수 1 |
| 2026-09-29 `delay-after`, 같은 `event-001` 수동 재전송 | 두 전송 모두 약 2초 후 timeout | 각 전송에서 timeout 전에 처리 완료. 같은 프로세스의 처리 건수 1 → 2 |

Sender는 제한 시간 안에 응답을 확인하지 못했지만, Receiver 로그에서는 실제 처리가 확인됐다. Receiver의 응답 시도 로그는 Sender가 응답을 수신했다는 증거가 아니다. 또한 같은 Event ID가 헤더에 있어도 Receiver에 중복 검사 로직이 없으면 동일한 논리적 이벤트가 다시 처리될 수 있었다.

이 결과는 모든 timeout에서 Receiver가 처리한다는 뜻이 아니다. 관찰한 것은 timeout만으로 실제 처리 여부를 확정할 수 없고, 처리 여부가 불확실한 요청을 재전송하면 중복 처리가 발생할 수 있다는 점이다.

실험 출처는 [HTTP 직접 전달 실험](https://github.com/gumasaje/irezumi/blob/293db7fb5bf5853200ca9a7b707972016ebc7a85/http/direct-delivery/README.md)이며, 참조 커밋은 `293db7fb5bf5853200ca9a7b707972016ebc7a85`다. 상세 구성과 실행 로그는 원본 문서에 있으며, 원본 로그의 시각은 UTC다. 실험 코드는 같은 커밋의 [SenderMain.java](https://github.com/gumasaje/irezumi/blob/293db7fb5bf5853200ca9a7b707972016ebc7a85/http/direct-delivery/src/main/java/SenderMain.java)와 [ReceiverMain.java](https://github.com/gumasaje/irezumi/blob/293db7fb5bf5853200ca9a7b707972016ebc7a85/http/direct-delivery/src/main/java/ReceiverMain.java)에서 확인할 수 있다.

## 초기 요구사항

### R1. 접수 이후 전달 작업 유지와 재시작 후 복구

> Retryver는 접수 완료라고 응답한 이벤트에 대해, Publisher의 HTTP 요청이 종료된 이후에도 전달할 이벤트와 남은 전달 작업을 유지하고 관리해야 한다. Retryver 프로세스가 중단되더라도 접수 완료한 전달 작업을 잃지 않아야 하며, 재시작 후 남은 작업을 다시 이어갈 수 있어야 한다.

접수 완료는 Retryver가 해당 전달 작업의 책임을 맡았다는 의미다. 이 책임은 Publisher의 HTTP 요청이 끝나거나 Retryver 프로세스가 중단됐다는 이유로 사라지지 않는다. 따라서 전달 작업을 Publisher 요청의 수명과 분리해 유지하고, 프로세스 재시작 후에도 남은 작업을 복구할 수 있어야 한다.

이 요구사항은 사전 실험의 관찰 결과와 구분되며, Retryver가 접수한 전달 작업을 책임진다는 서비스 책임에서 도출한다.

### R2. timeout과 실제 처리 결과 구분

> Retryver는 Receiver로 보낸 요청에서 timeout이 발생했을 때, 해당 이벤트가 Receiver에서 처리되지 않았다고 단정해서는 안 된다.

`delay-before`에서는 Sender의 timeout 이후 Receiver가 처리했고, `delay-after`에서는 Receiver의 처리가 끝난 뒤 Sender가 timeout을 관찰했다. 두 경우 모두 timeout만으로 Receiver의 처리 여부를 확정할 수 없었다. Retryver는 송신자가 관찰한 통신 결과와 수신자의 실제 처리 결과를 구분해야 한다.

### R3. 재전송 사이의 논리적 이벤트 식별 유지

> Retryver는 동일한 이벤트를 여러 번 전달하더라도 최초 전달과 이후 재전송을 동일한 논리적 이벤트에 대한 전달 시도로 식별할 수 있어야 한다.

같은 `event-001`의 수동 재전송에서 Receiver의 처리 건수가 1에서 2로 증가했다. 중복 가능성을 다루려면 같은 논리적 이벤트와 그 이벤트를 보내는 여러 시도를 구분하고 연결할 수 있어야 한다. 다만 식별 정보만으로 중복 처리가 방지되는 것은 아니다.

## 접수·전달 경계에 대한 잠정안

접수·전달 방식의 후보는 다음과 같다.

1. Receiver의 응답까지 기다린 뒤 Publisher에게 응답한다.
2. 메모리에 전달 작업을 보관한 뒤 Publisher에게 응답한다.
3. 재시작 후 복구 가능한 형태로 전달 작업을 기록한 뒤 Publisher에게 응답하고, 별도로 전달한다.

메모리에만 전달 작업을 보관하면 Publisher의 HTTP 요청이 끝난 뒤에도 작업을 유지할 수 있지만, Retryver 프로세스가 중단되면 작업을 잃을 수 있다. 따라서 메모리만으로 보관하는 방식은 재시작 후 복구까지 요구하는 R1을 충족하지 못한다.

접수 완료로 응답하려면 그 전에 전달할 이벤트와 남은 작업이 재시작 후에도 복구 가능한 형태로 기록되어 있어야 한다. 이에 따라 작업을 기록한 뒤 접수 완료로 응답하고, 별도로 전달하는 방식을 잠정안으로 선택한다.

### 접수 완료의 잠정 조건

Event와 해당 Receiver로의 Delivery가 모두 재시작 후에도 복구 가능한 형태로 기록되어 있어야 한다. 이 조건을 충족하면 아직 미전송이어도 접수 완료로 응답할 수 있다. Event만 기록되고 Delivery 기록에 실패한 경우에는 이 접수 조건을 충족하지 못한다.

접수 완료는 Retryver가 전달 작업을 맡았다는 의미다. Receiver의 응답 확인과 업무 처리 완료는 별개의 결과다.

### Event와 Delivery를 구분하는 이유

- Event는 전달하려는 논리적 이벤트 자체를 가리킨다. 이벤트 ID와 내용처럼 전달 대상이 달라도 공통인 정보에 해당한다.
- Delivery는 그 이벤트를 특정 Receiver로 보내야 하는 작업을 가리킨다. 전달 대상과 그 대상으로 보냈을 때 관찰한 결과처럼 대상별로 구분할 정보에 해당한다.

예를 들어 같은 이벤트를 Receiver A와 B로 보냈을 때, A에서는 204 응답을 확인하고 B에서는 timeout이 발생했다고 가정하자. 이벤트에 성공 또는 실패 하나만 표시하면 대상별 결과가 사라진다. 이는 두 책임을 구분하기 위한 예시이며, 실제 실험 결과는 아니다.

### 전달 작업의 상황

- 접수 후 미전송: 접수에 필요한 기록은 완료됐고 아직 전송하지 않은 작업.
- 성공 응답 확인: Receiver의 204 응답을 확인한 경우. Receiver의 업무 처리 완료를 뜻하는지는 Receiver와의 계약에 달려 있다.
- 응답 미확인: timeout으로 응답을 확인하지 못한 경우. 실제 처리 여부는 불확실하게 남긴다.

응답을 확인하지 못한 뒤 다시 보낼지, 언제 종료할지는 남은 설계 질문으로 둔다.

## 책임의 범위와 한계

Publisher의 Retryver 접수 요청과 Retryver의 Receiver 전달 요청은 서로 다른 HTTP 요청이다. 접수 완료의 잠정 조건은 전달 작업을 맡기 위한 기록의 완료이며, Receiver의 업무 처리 완료를 의미하지 않는다.

Retryver는 재전송 시 동일한 논리적 이벤트임을 Receiver가 식별할 수 있는 정보를 유지할 수 있지만, Receiver가 이를 이용하지 않는 경우 Receiver 내부의 중복 처리를 단독으로 방지할 수 없다.
